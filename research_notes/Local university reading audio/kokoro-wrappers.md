# Kokoro TTS wrappers

Research date: 15 November 2026. Primary pages were fetched that day. Anything the sources themselves date before July 2025 is flagged as possibly stale.

Upstream weight release used by these projects: [hexgrad/Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M). The model card lists v1.0, published 27 January 2025, 82 million parameters, 8 languages and 54 voices, SHA256 prefix `496dba11`, Apache-licensed weights, StyleTTS 2 plus ISTFTNet, decoder only. v0.19 (25 December 2024) is the prior release: under 100 hours, 1 language, 10 voices. The card’s usage snippet installs `kokoro>=0.9.2`, `soundfile`, and `espeak-ng`, and writes 24 kHz WAV. The same card says, in a paragraph it dates “As of April 2025,” that on average 1,000 characters of input is about 1 minute of output. That duration rule and the API price next to it are older than mid-2025. The card does not publish RAM, VRAM, CPU cores, RTF, or a MOS. Quality wording on the card is “comparable quality to larger models” and “significantly faster and more cost-efficient,” with no named cloud product and no NotebookLM comparison. Code repo [hexgrad/kokoro](https://github.com/hexgrad/kokoro) last push recorded on the GitHub API: 6 August 2025 (10,119 stars, Apache-2.0, 223 open issues). That upstream code push is just after mid-2025 and is old relative to November 2026; the listed weight release is still v1.0 from January 2025.

## What engine and model weights does each project run?

### Takeaway
Four projects synthesize with Kokoro-82M from hexgrad. audio.cpp and LocalText2Voice are multi-engine applications that include Kokoro among many other models. PierrunoYT and nazdridoy are Kokoro applications. hangry-labs/kokoroTTS is a maintained fork of hexgrad/kokoro that also loads extra Kokoro-family checkpoints.

### Cited Findings
- **0xShug0/audio.cpp** is a pure C++ ggml audio engine, not a Python Kokoro wrapper. GitHub API on 15 November 2026: not a fork, not archived, C++, created 23 June 2026, pushed 15 November 2026, 4,236 stars, 516 forks, 14 open issues. README: 148 model families, CLI plus server API, no Python dependency. Kokoro is one family: `kokoro_tts`, languages en-us, en-gb, es, fr, hi, it, ja, pt-br, zh, described as Kokoro 82M, loadable as safetensors or local GGUF BF16/Q8, with streaming. The model doc says audio.cpp packages Kokoro 82M as GGUF with all 54 upstream voice packs, default package `kokoro_82m_q8_0` (`models/Kokoro-82M-GGUF/kokoro-82m-q8_0.gguf`), also `kokoro_82m_bf16`. Conversion command is `tools/models/prepare_kokoro_gguf.py --source` pointing at an official `hexgrad/Kokoro-82M` checkout. The speed-capable GGUF is the one published on Hugging Face on 22 September 2026 (UTC) or later. — [GitHub API](https://api.github.com/repos/0xShug0/audio.cpp); [README](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/README.md); [docs/models/kokoro_tts.md](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/docs/models/kokoro_tts.md)
- **PierrunoYT/Kokoro-TTS-Local** is not a GitHub fork (`fork: false`). API: Python, created 14 January 2025, pushed 7 October 2026, default branch `master`, 371 stars, 65 forks, 0 open issues, Apache-2.0. README: local synthesis with Kokoro-82M, automatic download from Hugging Face, model file `kokoro-v1_0.pth`, 24 kHz, 82M parameters, repository [hexgrad/Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M), 54 voices across 9 languages (American and British English, Japanese, Mandarin, Spanish, French, Hindi, Italian, Brazilian Portuguese). Mandarin uses a separate setup (`kokoro-tts-setup` / `setup_chinese_tts`). It also tells users they can `pip install kokoro soundfile` plus espeak. — [GitHub API](https://api.github.com/repos/PierrunoYT/Kokoro-TTS-Local); [README](https://raw.githubusercontent.com/PierrunoYT/Kokoro-TTS-Local/master/README.md)
- **hangry-labs/kokoroTTS** is a GitHub fork of [hexgrad/kokoro](https://github.com/hexgrad/kokoro). API: created 27 March 2026, pushed 30 October 2026, Python, Apache-2.0, 28 stars, 5 forks, 0 open issues. README: Docker images with browser UI and HTTP API; canonical model id `kokoro`, with aliases `kokoro-82m`, `kokorotts`, and `hexgrad/Kokoro-82M`. Full image contains the standard Kokoro model, two German checkpoints (Kikiri German Martin and Victoria, Apache-2.0), ContextBoxAI Kokoro Vietnamese (Apache-2.0, 14 voices, `vig2p`), and [Kokoro-82M-v1.1-zh](https://huggingface.co/hexgrad/Kokoro-82M-v1.1-zh) (Apache-2.0, 100 numbered Chinese voices plus English Maple, Sol, and Vale). README counts 173 voice packs in the full image and, in the deployment section, 54 standard plus 14 Vietnamese plus 103 v1.1 Chinese/English voices. Five packs load independently and lazily. Parent hexgrad/kokoro `pushed_at` on the same API response: 6 August 2025. — [GitHub API](https://api.github.com/repos/hangry-labs/kokoroTTS); [README](https://raw.githubusercontent.com/hangry-labs/kokoroTTS/main/README.md)
- **estebanstifli/localtext2voice** resolves to repo name `LocalText2Voice` (GitHub is case-insensitive). API: not a fork, Python, MIT, created 11 June 2026, pushed 7 November 2026, 422 stars, 33 forks, 4 open issues. README: desktop app whose local narration engines include Piper, Kokoro, Chatterbox, Qwen3 TTS, OmniVoice, IndexTTS-2.5, and optional non-commercial F5-TTS Russian, plus optional cloud APIs (OpenAI TTS, ElevenLabs, Google Gemini TTS, Azure Speech). Kokoro is “local/offline CPU/CUDA” and “uses embedded Python runtime”; “Kokoro local models: downloaded on demand, license depends on the model.” It also embeds selected [audio.cpp](https://github.com/0xShug0/audio.cpp) models (Higgs Audio v3, Fish Audio S2 Pro, Breeze TTS 2, VoxCPM 2) via a shared native runtime. The README does not name the Kokoro checkpoint filename or the hexgrad repo in the sections read. Topics include `kokoro`. — [GitHub API](https://api.github.com/repos/estebanstifli/LocalText2Voice); [README](https://raw.githubusercontent.com/estebanstifli/localtext2voice/main/README.md)
- **nazdridoy/kokoro-tts** is not a GitHub fork. API: Python, MIT, created 14 January 2025, pushed 22 August 2026, 2,013 stars, 185 forks, 19 open issues. Homepage field is the hexgrad model page. README: CLI using “the Kokoro model”; user must download `voices-v1.0.bin` and `kokoro-v1.0.onnx` from this repo’s GitHub release `v1.0.0`. It does not list the Spanish, Hindi, or Brazilian Portuguese voices that Pierruno and audio.cpp document. Latest GitHub release is `v2.3.2`, published 22 August 2026, a dependency and PyMuPDF fix, with no release assets. — [GitHub API](https://api.github.com/repos/nazdridoy/kokoro-tts); [README](https://raw.githubusercontent.com/nazdridoy/kokoro-tts/main/README.md); [releases](https://api.github.com/repos/nazdridoy/kokoro-tts/releases?per_page=3)

### Inferences
- audio.cpp is a different engine (ggml/GGUF) that converts hexgrad Kokoro-82M weights. It is not a thin wrapper and not a fork of hexgrad/kokoro.
- PierrunoYT is an application wrapper around the official PyTorch Kokoro stack (`kokoro-v1_0.pth`), with its own CLI, Gradio UI, and Docker. Not a fork.
- hangry-labs is a fork of the upstream library, extended into a product (Docker, UI, API, extra language checkpoints). Not abandoned as of late October 2026.
- LocalText2Voice is a different application entirely. Kokoro is one installable engine inside it. Which exact Kokoro file it downloads was not in the README sections retrieved.
- nazdridoy is a CLI wrapper around the ONNX export (`kokoro-v1.0.onnx` via kokoro-onnx), not the PyTorch pipeline and not a fork. The ONNX file is distributed from nazdridoy’s own `v1.0.0` release; the README does not restate the hexgrad SHA256.

### Gaps
- LocalText2Voice’s README, as fetched, does not name `Kokoro-82M`, `kokoro-v1_0.pth`, or an ONNX file. The engine is only identified as Kokoro.
- Whether nazdridoy’s `kokoro-v1.0.onnx` byte-matches a specific hexgrad or thewh1teagle export was not checked.
- No new Kokoro weight version after v1.0 (27 January 2025) appears on the hexgrad model card. Hangry’s v1.1-zh and German/Vietnamese checkpoints are separate HF repos, not a new row on that card.

## Does it accept .md, .txt, and .pdf, or only raw text / one format?

### Takeaway
Only LocalText2Voice documents `.txt` and `.md`. Only nazdridoy documents `.pdf` and `.txt`. None of the five document all three of `.md`, `.txt`, and `.pdf`. The other three take text strings (CLI flag, typed prompt, or HTTP/UI field), not those document types.

### Cited Findings
- audio.cpp Kokoro quick start uses `--text "Hello from Kokoro."` and an HTTP `input` string. The Kokoro model doc does not mention `.md`, `.txt`, or `.pdf`. — [kokoro_tts.md](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/docs/models/kokoro_tts.md)
- PierrunoYT CLI is an interactive menu: the user types the sentence at a prompt. The web UI has a text input field. Documented outputs are WAV, MP3, and AAC. No `.md`, `.txt`, or `.pdf` input is described. — [README](https://raw.githubusercontent.com/PierrunoYT/Kokoro-TTS-Local/master/README.md)
- hangry-labs: browser generation plus JSON `input` on an OpenAI-compatible endpoint and a native API. Default `input_type` is `text`. SSML is opt-in (`input_type: ssml`) and is not auto-detected. Documents are limited to 50,000 characters when SSML is used. No `.md`, `.txt`, or `.pdf` ingestion is described in the README sections retrieved. — [README](https://raw.githubusercontent.com/hangry-labs/kokoroTTS/main/README.md)
- LocalText2Voice: “Paste long text directly into the editor. Import `.txt`, `.md`, `.docx`, and DRM-free `.epub`.” Chapter detection includes Markdown headings. PDF is not in that import list. — [README](https://raw.githubusercontent.com/estebanstifli/localtext2voice/main/README.md)
- nazdridoy input formats: `.txt`, `.epub`, `.pdf`, and stdin (`-`, `/dev/stdin`, or `CONIN$`). Usage is `kokoro-tts <input_text_file>`. `.md` is not listed. PDF support is marked done; GUI is still an open TODO. — [README](https://raw.githubusercontent.com/nazdridoy/kokoro-tts/main/README.md)

### Inferences
- A Markdown file could be spoken by nazdridoy only if the caller renames it to `.txt` or pipes it. That behavior is not documented.
- audio.cpp, PierrunoYT, and hangry-labs would speak a document only after some other program extracts the text. That step is outside these repos.

### Gaps
- Whether audio.cpp’ general CLI accepts a text file path, as opposed to the `--text` string shown for Kokoro, was not confirmed in the Kokoro model doc.
- Whether hangry’s browser UI has a file-upload control was not visible in the README excerpt. The documented contract is a text or SSML string.

## Published or reported RAM, VRAM, and CPU requirements? Will it run on 24 GB system RAM and 2 GB VRAM without a GPU upgrade?

### Takeaway
No repo publishes “2 GB VRAM” or “24 GB RAM” as a Kokoro requirement. The hexgrad card publishes neither RAM nor VRAM. Independent Kokoro measurements put process RAM around 0.7–2.5 GB and PyTorch/ONNX GPU peaks around 0.9–1.1 GB allocated, with one whole-GPU reading of about 2.6 GB and one multi-checkpoint Docker reservation of 2052 MiB. 24 GB system RAM is above every Kokoro RAM figure found. A 2 GB GPU is not something any source states will work; CPU backends are documented for all five, so a GPU upgrade is not required for the CPU path.

### Cited Findings
- Hexgrad model card: no RAM, VRAM, or CPU figure. — [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M)
- audio.cpp Kokoro doc: CPU backend is a documented quick start (`--backend cpu`). It does not state a minimum RAM or VRAM for Kokoro. It does publish host graph-arena defaults of 384, 256, and 640 MiB (metadata arenas, “do not size device workspace”). On an RK3588, measured peak RSS for `kokoro-82m-q8_0` went from 2777 MB to 2334 MB when the generator moved to the NPU (185 Russian characters, 4 threads); `gain=true` added 601 MB RSS. Those are SoC RSS figures, not desktop VRAM. README performance claims (1.8–8× vs Python, Q8 up to 37% lower peak VRAM, Supertonic 3 on an RTX 5090) are not Kokoro-specific. — [kokoro_tts.md](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/docs/models/kokoro_tts.md); [README](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/README.md)
- PierrunoYT: CUDA GPU is optional. No RAM, VRAM, or core-count number. Docker support is “CPU-first”; GPU images are “intentionally out of scope.” Python 3.10–3.12. — [README](https://raw.githubusercontent.com/PierrunoYT/Kokoro-TTS-Local/master/README.md)
- hangry-labs publishes CPU and NVIDIA GPU Docker commands, not a minimum RAM. Its own VRAM benchmark, labeled `v0.4-snapshot`, quiet RTX 5070 Ti (16303 MiB), 3 October 2026 03:20:48 UTC, all 70 voices and 11 languages: standard Kokoro weights before inference 317.6 MiB allocated and 332.0 MiB reserved; after lazy-loading German and Vietnamese checkpoints, process peak 1725.1 MiB allocated and 2052.0 MiB reserved. Whole-device usage rose from 1293.6 MiB idle to 3413.6 MiB, including the Windows display stack. Vietnamese `storyvert` set the process peak. A separate shared-GPU timing run (not a quiet-GPU record) reported mean 1.369 s, P95 2.308 s, 15.60× realtime across 350 requests. A dev-reload note says a duplicate-initialization supervisor dropped from roughly 1 GB to about 33 MB RSS; that is the launcher, not synthesis. — [README](https://raw.githubusercontent.com/hangry-labs/kokoroTTS/main/README.md); [VRAM benchmark page](https://hangry-labs.github.io/kokoroTTS/benchmarks/vram/VRAM_BENCHMARKS.html)
- LocalText2Voice states its profiles are “practical recommendations, not strict compatibility limits.” Basic: 64-bit 4-core CPU, 8 GB RAM, 5 GB disk, no dedicated GPU, for editing, cloud APIs, and lightweight local generation. Recommended: modern 6-core, 16 GB RAM, 20–30 GB SSD, NVIDIA CUDA GPU with 8 GB VRAM, for regular local neural TTS. High performance: 8-core or better, 32 GB RAM, 50 GB SSD, NVIDIA RTX with 12 GB or more VRAM, for larger models, long-form work, and speech verification. “Piper and Kokoro can run without a powerful GPU.” NVIDIA GPU is optional; other GPU families are not assumed to accelerate every engine. These numbers are not a Kokoro-only measurement. — [README](https://raw.githubusercontent.com/estebanstifli/localtext2voice/main/README.md)
- nazdridoy: “GPU Support” is a feature and a completed TODO. No RAM or VRAM number in the README. Python 3.11–3.12; 3.13+ “is not currently supported.”
- Independent Kokoro measurements (not these five repos):
  - tts-bench, rig explicitly labeled `windows-5090` (Ryzen 9 9950X3D, RTX 5090 32 GB, 126 GB RAM, Windows 11): Kokoro CUDA warm RTFx 103.68×, peak RAM 2.43 GB, peak VRAM 925 MB; Kokoro CPU warm RTFx 14.38×, peak RAM 1.82 GB, TTFA warm 532 ms. The page also has linux-3090 and mac-m4 rigs. Later Kokoro rows in the flattened extract (CUDA VRAM 879 MB and RAM 1.85 GB; CPU RAM 1.65 GB; MPS RAM 1.26 GB; another CPU row RAM 2.49 GB) are on that same page, but the extract dropped the rig headings, so those machines are not confirmed line-by-line. Prompt length is not in the extract, so these RTFx values cannot be turned into seconds per kilobyte from this page alone. Model release column says Dec 2024. — [tts-bench speed](https://5uck1ess.github.io/tts-bench/speed.html)
  - VRAM16, Kokoro-82M v1.0, RTX 5080 16 GB, Ryzen 7 9800X3D, 64 GB RAM, `kokoro` pip plus misaki, PyTorch 2.14.1+cu130: about 28 s of Japanese speech in 0.2 s on GPU and 4.6 s on CPU (4 threads); about 8 s of English in 1.17 s on that CPU. nvidia-smi whole-GPU peak about 2.6 GB, of which about 0.9 GB was already in use; PyTorch allocated about 1.1 GB. Weights described as 0.33 GB. First run about 3 s for the Japanese dictionary. — [VRAM16](https://vram16.ullu-egg.com/en/models/kokoro-82m/)
  - OpenVoiceIndex, 21 October 2026, cloud x86 VM, 8 vCPU Intel Xeon, 16 GB RAM, no GPU, kokoro-onnx, ~10–11 s English audio, median of 5 runs after warmup: fp32 RTF 0.1234 (stated as 8× realtime), TTFA 1.416 s, peak RAM 933.9 MB; int8 RTF 0.1480, peak RAM 744.0 MB. The page says this is not an N100 and an N100 should be several times slower. — [OpenVoiceIndex](https://openvoiceindex.com/models/kokoro-82m/on/x86-cpu/)
  - Hugging Face blog, VoxRT, Intel i9-13900K, WSL2, `kokoro-onnx` 0.6.1 fp32, texts of 44, 99, and 321 characters: RTF 51.7% of realtime on 1 thread and 17.2% on 4 threads; first audio 1.5 s short / 9.6 s for the ~17 s paragraph; peak RSS 1246 MB. The page says Kokoro synthesizes the whole utterance before returning. — [HF blog](https://huggingface.co/blog/VoxRT/small-cpu-text-to-speech-models-compared-piper-kok)
  - Big Iron guide: Kokoro fp32 0.42× realtime without AVX and 2.77× with AVX2, peak RAM 870 MB; Kokoro int8 0.24× without AVX and 0.71× with AVX2, peak RAM 670 MB. The page calls fp32 Kokoro the most natural of the small models in that comparison (espeak, Piper, Kitten, Chatterbox, Orpheus, Oute). CPU model names beyond “old (no AVX)” and “new (AVX2)” were not in the snippet. — [Big Iron](https://www.bigiron.cc/guides/speech-on-a-cpu-without-avx-piper-kokoro-whisper-and-why-int8-got-slower)

### Inferences
- 24 GB system RAM covers every published Kokoro process-RAM figure found (about 0.7–2.5 GB) with a wide margin. LocalText2Voice’s own table puts 24 GB between its 16 GB “recommended” profile and its 32 GB “high performance” profile. That is a comparison of their guidance to the target machine, not a measurement on 24 GB.
- A 2 GB GPU is inside the tts-bench Kokoro VRAM peaks (925 MB and 879 MB) and inside VRAM16’s PyTorch allocation (about 1.1 GB). It is not inside VRAM16’s whole-GPU nvidia-smi peak (about 2.6 GB) or hangry’s full-catalog reserved peak (2052 MiB, and that run also started from 1293.6 MiB already on the device). Those 2.6 GB and 2052 MiB figures were measured on 16 GB cards, so they do not prove failure on 2 GB, and the sub-1 GB figures were measured on 16–32 GB cards, so they do not prove success on 2 GB.
- CPU execution is the path that does not need a GPU upgrade. Every project documents a CPU route: audio.cpp `--backend cpu`, PierrunoYT CPU fallback and CPU-first Docker, hangry CPU image, LocalText2Voice “no dedicated GPU” plus Kokoro without a powerful GPU, nazdridoy as a Python ONNX CLI that also advertises optional GPU.
- Hangry’s 2052 MiB figure is the peak after several checkpoints had been loaded in one process. It is the wrong number to treat as the cost of one English voice. The only pre-inference standard-checkpoint figure they publish is 317.6 / 332.0 MiB. They do not publish the peak during a single standard-voice utterance.

### Gaps
- No source states a minimum VRAM, a test on a 2 GB GPU, or a test on a 24 GB RAM machine for these five repos.
- audio.cpp does not publish Kokoro desktop VRAM for Q8 or BF16.
- tts-bench prompt length was not in the extracted page, so its RTFx cannot be converted here into seconds per 1 KB.
- LocalText2Voice does not break RAM or VRAM out for Kokoro versus Chatterbox, Qwen3, or Whisper verification. The 8 GB profile says “lightweight local generation,” which the feature list associates with Piper and Kokoro, but it does not say Kokoro was measured at 8 GB.

## CLI, web UI, or both?

### Takeaway
audio.cpp, PierrunoYT, hangry-labs, and LocalText2Voice expose both a local interface and a programmatic surface. nazdridoy is CLI only; its README still has GUI unchecked.

### Cited Findings
- audio.cpp: `audiocpp_cli` and `audiocpp_server` with an embedded WebUI (`audiocpp_server --ui`, default `http://127.0.0.1:8080`). Kokoro is available on the CLI (`--family kokoro_tts`) and through `/v1/audio/speech`. Prebuilt binaries and Docker exist for CLI and server. — [README](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/README.md); [kokoro_tts.md](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/docs/models/kokoro_tts.md)
- PierrunoYT: `kokoro-tts` interactive CLI and `kokoro-tts-web` Gradio UI, typically port 7860. Docker maps 7860 and requires `KOKORO_TTS_USERNAME` and `KOKORO_TTS_PASSWORD`. — [README](https://raw.githubusercontent.com/PierrunoYT/Kokoro-TTS-Local/master/README.md)
- hangry-labs: browser UI plus HTTP API on port 7860, OpenAI-compatible and native routes, optional MCP at `/mcp`. Docker is the documented install. A Python client exists (`kokorotts` from git tag `v1.0`) but it talks to a running server. — [README](https://raw.githubusercontent.com/hangry-labs/kokoroTTS/main/README.md)
- LocalText2Voice: desktop UI (Windows installer; Linux from source with a launcher). No Kokoro CLI is described. Workflow is import or write, generate, review, mix, optional video storyboard. — [README](https://raw.githubusercontent.com/estebanstifli/localtext2voice/main/README.md)
- nazdridoy: CLI only. TODO list: GPU done, PDF done, GUI not done. PyPI command `kokoro-tts`. — [README](https://raw.githubusercontent.com/nazdridoy/kokoro-tts/main/README.md)

### Inferences
- For a batch reading pipeline, nazdridoy and audio.cpp are the ones whose documented interface is a non-interactive command over a text payload. PierrunoYT’s CLI, as documented, is a menu that asks for text on stdin of the program, not a file argument.

### Gaps
- Whether PierrunoYT accepts a non-interactive one-shot file argument was not in the README usage section, which only shows the menu.

## Does synthesis speak the supplied text verbatim, or does an LLM rewrite, summarize, or podcast-ify it?

### Takeaway
All five speak the text they are given. None document an LLM that rewrites, summarizes, or turns the source into a NotebookLM-style overview. “Podcast” in LocalText2Voice means a music mix under the narration. Chunking, G2P, normalization, and SSML change pronunciation or pauses, not the wording, except where a user types markup.

### Cited Findings
- audio.cpp Kokoro: the CLI speaks `--text`. Chunk size defaults are 240 characters, or 100 for Chinese and Japanese, to stay under a 510-symbol phoneme limit. Built-in G2P is eSpeak for several languages. The doc warns that timestamp groups are phonemes, not words, and that eSpeak merges some function words. No LLM step is described. — [kokoro_tts.md](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/docs/models/kokoro_tts.md)
- PierrunoYT: the user enters the sentence; the program generates speech for that string. A 7 October 2026 commit splits long Chinese and Japanese lines into pieces of at most 80 characters because Kokoro’s non-English chunker only split on ASCII `.!?` and truncated phonemes at 510. That is segmentation. The README does not describe a rewrite or summary model. — [README](https://raw.githubusercontent.com/PierrunoYT/Kokoro-TTS-Local/master/README.md); [commit](https://github.com/PierrunoYT/Kokoro-TTS-Local/commit/c6501063c0c686d44167d4b669496ef63c888b0e)
- hangry-labs: default input is text. Non-empty OpenAI `instructions` return an error rather than being applied. “Kokoro does not support natural-language instructions.” SSML is explicit opt-in for prosody, breaks, and phonemes. Magic Studio edits dialogue the user writes (takes, voice, prosody). The README says unsupported voice-design, cloning, and delivery directions fail clearly. No summarizer is described. — [README](https://raw.githubusercontent.com/hangry-labs/kokoroTTS/main/README.md)
- LocalText2Voice: “import or write a script, generate narration.” Optional normalization “prepares a pronunciation-friendly copy before generation without changing the source text.” Audio Mix “keep[s] the clean narration file untouched” and adds music, ducking, and loudness; the README calls this podcast-ready. Roadmap item still open: “Optional LLM-assisted course/script generation.” A tree comment says `llm/` is a “Future LLM provider interface.” Video storyboard can use an external agent to write scene prompts from timings; the README says “No internal narrative analysis is required.” — [README](https://raw.githubusercontent.com/estebanstifli/localtext2voice/main/README.md)
- nazdridoy: reads `.txt`, extracts EPUB chapters, extracts PDF text, chunks, and synthesizes. Features are voices, blending, speed, wav/mp3, and chapter split. No LLM, summary, or podcast-script feature is listed. — [README](https://raw.githubusercontent.com/nazdridoy/kokoro-tts/main/README.md)
- Hexgrad’s own example passes a string straight into `KPipeline`. — [model card](https://huggingface.co/hexgrad/Kokoro-82M)

### Inferences
- For university reading, these tools will attempt to read the supplied wording. They will not produce a NotebookLM audio overview unless some other program rewrites the text first.
- Pronunciation will still differ from the printed page: numbers, abbreviations, Roman numerals, and G2P errors are spoken forms, not a second draft. nazdridoy has open bugs of that kind (below).

### Gaps
- LocalText2Voice’s unchecked LLM roadmap does not say the feature is absent from every code path, only that the README still lists it as not done. The fetched README does not show a control that summarizes a document before Kokoro speaks it.
- No source describes Markdown being stripped to speech-clean prose. If `.md` is imported by LocalText2Voice, heading detection is documented; whether hash marks are spoken was not stated.

## Real-time factor or words-per-second, against under 30 seconds of processing per 1 KB of source text

### Takeaway
No repo publishes words per second or seconds per kilobyte of source. Published Kokoro speed is RTF or RTFx on short clips, and those rates are many times realtime on the tested desktop CPUs. The 30-second-per-1 KB bar is met on those machines only by combining their RTF with the model card’s “1,000 characters ≈ 1 minute” average. A no-AVX CPU measurement at 0.42× realtime would miss that bar. That combination is an inference, and the 1,000-character rule is from an April 2025 note.

### Cited Findings
- Hexgrad card, in text it dates “As of April 2025”: average 1,000 characters of input is about 1 minute of output. No RTF on the card. Possibly stale. — [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M)
- hangry-labs, RTX 5070 Ti, shared with an idle Qwen container, 350 requests, 70 voices: mean 1.369 s, P95 2.308 s, 15.60× realtime. The README does not say how long each utterance was. — [README](https://raw.githubusercontent.com/hangry-labs/kokoroTTS/main/README.md)
- tts-bench `windows-5090`: Kokoro CUDA warm 103.68× realtime (TTFA warm 67 ms, peak VRAM 925 MB); Kokoro CPU warm 14.38× (TTFA warm 532 ms, peak RAM 1.82 GB). Prompt length not in the extract. — [tts-bench](https://5uck1ess.github.io/tts-bench/speed.html)
- VRAM16: 28 s Japanese audio in 0.2 s on an RTX 5080 and in 4.6 s on CPU, 4 threads (about one sixth of realtime, their wording). 8 s English in 1.17 s on that CPU. — [VRAM16](https://vram16.ullu-egg.com/en/models/kokoro-82m/)
- OpenVoiceIndex, 21 October 2026, 8 vCPU Xeon, no GPU, ~10–11 s audio: kokoro-onnx fp32 RTF 0.1234, int8 RTF 0.1480. They define RTF as wall-clock processing time divided by audio duration, excluding model load. — [OpenVoiceIndex](https://openvoiceindex.com/models/kokoro-82m/on/x86-cpu/)
- VoxRT HF blog, i9-13900K, kokoro-onnx 0.6.1 fp32: RTF 51.7% of realtime (1 thread) and 17.2% (4 threads). A ~17 s paragraph took 9.6 s to first audio on the 1-thread setup because the utterance is synthesized before return. — [HF blog](https://huggingface.co/blog/VoxRT/small-cpu-text-to-speech-models-compared-piper-kok)
- Big Iron: Kokoro fp32 2.77× with AVX2 and 0.42× without AVX; int8 slower than fp32 (0.71× with AVX2, 0.24× without). — [Big Iron](https://www.bigiron.cc/guides/speech-on-a-cpu-without-avx-piper-kokoro-whisper-and-why-int8-got-slower)
- audio.cpp README speed claims are for other models or for “selected TTS paths,” not a Kokoro RTF. The Kokoro doc’s only wall-clock figures are RK3588 NPU comparisons (RTF 1.415 to 0.867 on a 185-character Russian clip, 4 threads), which is still slower than realtime on that board. — [README](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/README.md); [kokoro_tts.md](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/docs/models/kokoro_tts.md)
- None of the five READMEs state words per second.

### Inferences
- Using the card’s 1,000 characters ≈ 60 seconds of audio, and treating 1 KB of ASCII as about 1,000 characters: processing time ≈ 60 / (realtime multiple) seconds per 1 KB.
  - windows-5090 CPU 14.38× → about 4 seconds.
  - Xeon fp32 RTF 0.1234 → about 7.5 seconds.
  - i9-13900K, 4 threads, RTF 0.172 → about 10 seconds.
  - i9-13900K, 1 thread, RTF 0.517 → about 31 seconds, just over the 30-second bar.
  - AVX2 2.77× → about 22 seconds, under the bar.
  - no-AVX 0.42× → about 143 seconds, over the bar.
- Those products assume the April 2025 character-to-duration average still holds and that 1 KB equals 1,000 characters. A UTF-8 page with multibyte characters is fewer characters per kilobyte. University prose with numbers and headings was not the measured input.
- On a recent desktop CPU, the published Kokoro ONNX/PyTorch rates are in the “several times realtime” range, which is the regime that satisfies a 30-second budget for one kilobyte if the 1,000-character rule is right. A weak or no-AVX CPU is the case that does not.
- audio.cpp’s RK3588 figure (RTF still above 0.8) would not meet the bar for a 60-second utterance. That is an embedded board, not the 24 GB desktop target.

### Gaps
- No measurement of wall time per 1 KB of markdown, PDF, or a real reading was found for any of the five repos.
- Words per second: not stated.
- tts-bench utterance duration: not in the extracted page.
- hangry’s 15.60× figure has no published clip duration.

## Voice naturalness relative to cloud TTS and to NotebookLM audio overviews

### Takeaway
No fetched source compares these repos, or Kokoro-82M, to NotebookLM audio overviews or to a named cloud TTS product with a listening score. The model card’s quality claim is “comparable quality to larger models,” without numbers. PierrunoYT’s A–F grades are training-data grades, not a cloud comparison. Kokoro speaks the source; NotebookLM audio overviews are a different product that discusses a source.

### Cited Findings
- Hexgrad card: “delivers comparable quality to larger models while being significantly faster and more cost-efficient.” No MOS, no ElevenLabs, OpenAI, Google, Azure, or NotebookLM mention. - PierrunoYT prints per-voice grades from A (`af_heart`) down to F+ (`am_adam`) and says: “Quality grades (A to F) indicate the overall quality based on training data quality and duration. - Big Iron, qualitative, inside a small-model CPU table: “Kokoro fp32 … Most natural voice of the small models,” compared there with espeak-ng, Piper, Kitten, Chatterbox, Orpheus, and Oute, not with cloud TTS or NotebookLM. — [Big Iron](https://www.bigiron.cc/guides/speech-on-a-cpu-without-avx-piper-kokoro-whisper-and-why-int8-got-slower)

Its “podcast” output is narration plus music. — [README](https://raw.githubusercontent.com/estebanstifli/localtext2voice/main/README.md)
- audio.cpp points at the Open TTS Leaderboard for streaming latency, not for a Kokoro naturalness score. The README sentence is “among the fastest inference engines for streaming TTS latency.” — [README](https://raw.githubusercontent.com/0xShug0/audio.cpp/main/README.md)

### Inferences
- Naturalness relative to cloud TTS and to NotebookLM is not established by these sources. The only sourced quality ordering is among small local models, where one guide ranks Kokoro fp32 as the most natural of that set, and among Kokoro’s own voices, where training-data grades put `af_heart` at the top.
- Because these programs speak the supplied text rather than writing an overview, they will not sound like a NotebookLM audio overview even if the voice is natural. That follows from the verbatim finding above, not from a listening test.
